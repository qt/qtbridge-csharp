# QML Language Server Metadata Update Plan

## Goal

Move Qt Bridge-specific QML language-server metadata generation into the build output so every
editor integration can consume the same qmlls-ready artifacts. The Visual Studio extension should
eventually stop patching `.qmlls.build.ini` and generating bridge-specific qrc files itself.

## Current State

- `qtbridge-qml.ide.json` is generated by `QtBridgeWriteQmlMetadataFile`.
- The Visual Studio extension reads that metadata, waits for `.qmlls.build.ini` and generated
  `.qmltypes`, then patches `.qmlls.build.ini`.
- The extension currently generates `.qt/qtbridge_project_sources.qrc` from `qml.files` and adds
  it to the project-source-root alias section.

This fixes Visual Studio, but the bridge-specific mapping still lives in one editor integration.

## Ideal State

The build produces complete qmlls-ready metadata:

- `qtbridge-qml.ide.json`
- `.qt/qtbridge_project_sources.qrc`
- a fully patched `.qt/.qmlls.build.ini`
- `.qt/qtbridge-qmlls.ready`

Editor integrations only need to wait for the ready marker, start or restart qmlls, and send the
build directory via `$/addBuildDirs`.

## Tasks

1. Keep `qml.files` in `qtbridge-qml.ide.json`.
   It records original QML file paths and generated module identity.

2. Add an MSBuild target after `QtBridgeBuild`, for example `QtBridgePrepareQmllsMetadata`.
   It must run after CMake has generated `.qt/.qmlls.build.ini`, generated `.qmltypes`, and module
   `qmldir` files.

3. Generate `.qt/qtbridge_project_sources.qrc` in that target.
   Map each original project QML file to `/qt/qml/<module>/File.qml`.

4. Patch `.qt/.qmlls.build.ini` in that target.
   Add or update the project-source-root alias section. Copy the generated source section's
   `importPaths` and `resourceFiles`, then append `qtbridge_project_sources.qrc` to
   `resourceFiles`.

5. Add `.qt/qtbridge-qmlls.ready`.
   Write this marker only after the qrc exists, `.qmlls.build.ini` is patched, and generated
   `.qmltypes` files are present and readable.

6. Extend `qtbridge-qml.ide.json` if useful.
   Consider adding explicit paths such as `qmlls.readyFile`, `qmlls.projectSourcesQrc`, or
   `qmlls.buildIni`.

7. Simplify the Visual Studio extension.
   Remove qrc generation and `.qmlls.build.ini` mutation from the extension. Keep only metadata
   discovery, ready-marker watching, qmlls restart, workspace folder registration, and
   `$/addBuildDirs`.
   On later builds, the extension should react to metadata or ready-marker changes, not to broad
   large numbers of unrelated build-directory file changes. A changed ready marker means the final
   `.qmlls.build.ini`, qrc, and `.qmltypes` set is complete and qmlls can be restarted/reloaded.

8. Add validation coverage.
   Add a build-level test or fixture that verifies:
   - `qml.files` includes newly added QML files.
   - `qtbridge_project_sources.qrc` maps original files to `/qt/qml/<module>/...`.
   - `.qmlls.build.ini` has the project-source-root alias section.
   - the alias section references `qtbridge_project_sources.qrc`.
   - `qtbridge-qmlls.ready` is written after the final artifacts are ready.

9. Verify editor behavior.
   Rebuild ColorPalette, open root-level QML files without `import Application`, and confirm qmlls
   resolves Application-module types without diagnostics.

10. Document the editor integration contract.
    Any editor integration should wait for `qtbridge-qmlls.ready`, then pass the build directory
    to qmlls. It should watch or poll the metadata/ready marker for subsequent builds and restart
    or reload qmlls only after the marker changes. It should not need Qt Bridge-specific
    source-to-resource mapping logic.
